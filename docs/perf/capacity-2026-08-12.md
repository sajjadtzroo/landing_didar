# Capacity & Scalability Report — didar-gold-api (2026-08-12)

**Environment:** local (MacBook, 11 cores) — uvicorn workers 1/2/4 against the
compose Postgres (:5434), isolated `didar_loadtest` DB seeded with **510 products**
(50× production catalog). Client = `ab` 2.3 (keep-alive), same host.
**Caveats:** client and server share the host (numbers are conservative at 4
workers); this measures the *code*, not Liara's vCPU quota — absolute prod
numbers will be lower on smaller vCPUs, but shapes/ratios (knee, scaling
efficiency, bottleneck identity) transfer.

## §2 Static review (before any test)

| Check | Status |
|---|---|
| Sync-in-async (requests, sleep, bcrypt, pandas) | ✅ clean — argon2/QR/MinIO all via `asyncio.to_thread` |
| Shared httpx client | ⚠️ per-call `AsyncClient` in `shared/sms.py`, `orders/notifications/sms.py`, `pricing/service.py` — harmless at current volume (SMS per OTP; scrape 1/120 s); pool it if OTP traffic spikes |
| Pool math | ⚠️ `(10+10) × workers × replicas ≤ 100` (`max_connections`). Observed 56 open conns under load at 4 workers. **2 replicas × 2 workers = 80 → at the edge; add PgBouncer before a 3rd replica** |
| In-process state | ⚠️ cache + rate-limiter fall back to per-process dicts when `REDIS_URL` unset — multi-replica correctness requires Redis in prod env |
| Unbounded queries | ⚠️ public `GET /products` returns the whole catalog (no pagination). Cached 60 s, so the DB is safe — but response CPU/size grows with catalog size (measured below). Keyset-paginate when the catalog reaches ~1k |
| BackgroundTasks weight | ✅ acceptable — CSV import is admin-only/rare (known ponytail ceiling in `import_job.py`) |
| N+1 / indexes | ✅ hot public reads are single indexed queries (slug unique-indexed) |

## Phase 6 isolation — where the ceiling lives

- `/health` ceiling ≈ detail ceiling (~2,100 RPS total) with client CPU at 16% →
  the limit is the **per-request framework overhead** (uvicorn+h11, 2 middlewares,
  request-context logging, Prometheus labels ≈ ~1.9 ms CPU/request/worker), not
  the DB and not the client.
- `pg_stat_activity` under load: 1 active, no `Lock` waits. The DB is nowhere
  near its wall at these rates.
- list endpoint: RPS identical at every concurrency (185/389/690 at 1/2/4
  workers) with p95 growing linearly — classic single-resource CPU knee. The
  cost is **Pydantic re-validation + JSON of 510 products per request even on
  cache hits** (`cache_get` returns objects that FastAPI re-serializes).

## Summary

```
Single worker capacity ......... list 185 RPS @ p95 84 ms · detail 760 RPS @ p95 16 ms
Knee concurrency ............... list c≈4 · detail c≈8 (per worker)
Scaling efficiency @ 4 workers . 0.93 (list — the governing path)
Sustainable RPS (2-worker prod-equivalent) ... ~390 list / ~1,800 detail
→ Concurrent users (Z=8 s) ..... ~3,100 (list-heavy mix, 2 workers: 390 × 8.08)
→ Supported DAU (§0 formula, 6 pages × 4 calls, peak 0.20, burst 2.5) ... ≈ 84,000 DAU
Primary bottleneck ............. per-request CPU (serialization + middleware), NOT Postgres
Headroom vs. today's traffic ... ≥ 100× (storefront is far below 390 RPS)
```

## Recommendations (in value order)

1. **Nothing is urgent.** Current traffic is orders of magnitude below capacity;
   the architecture scales linearly when needed.
2. When the catalog grows past ~1k items or list p95 nears 500 ms: paginate
   public `/products` (keyset) **or** cache the serialized JSON bytes (skip
   re-validation on hit) — that alone should ~4× the list ceiling.
3. Before a 3rd replica: PgBouncer (transaction mode) — pool math hits
   `max_connections` at `20 × workers × replicas`.
4. Confirm `REDIS_URL` is set on Liara so cache busts and rate limits are
   coherent across replicas.
5. Not run (candidates for a follow-up): Locust mixed-workload (Phase 4), soak/
   spike (Phase 5), and a staging-mirror run on Liara-sized vCPUs to convert
   these ratios into absolute prod numbers.

**Repeatability:** `backend/scripts/ab_sweep.sh <url> <n> <label> [c...]` emits
the CSV used here.
